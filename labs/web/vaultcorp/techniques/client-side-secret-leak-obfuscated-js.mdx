## Overview

A server sometimes ships a secret to the browser and leans on obfuscation —
Base64, XOR, a custom encoder, minified variable names — to make it feel
hidden. None of that is encryption. Anything the browser can decode, an
attacker can decode too, using the exact same function the page ships them.
The only real protection is to never send the secret to the client at all.

## Where it appears

- A "debug" or "diagnostics" script included on an authenticated page, meant
  for internal tooling but reachable by any logged-in user.
- A support or admin shortcut whose credential is pre-computed server-side
  and embedded in a script tag "for convenience."
- Feature flags or environment fixtures that happen to carry a token or key
  alongside harmless config values.
- Any place a developer reached for `atob()`, a XOR cipher, or a
  hand-rolled encoder and treated the result as if it were encrypted.

## Examples

### A single obvious token

The simplest case: a script sets `window.__apiToken = "ZmxhZ3t0b2tlbn0="`.
Base64-decoding it takes one line in the browser console. No real protection
was ever present — only an extra, trivially-reversed step.

### A decoy array

A more deceptive version returns several encoded entries instead of one —
for example a "staging" and a "production" fixture shuffled into random
order, all run through the same reversible transform. The decoy entries add
friction, not security: decoding all of them costs nothing extra, and the
real one is still fully recoverable. Spotting this pattern — several
same-shaped encoded blobs, one small shared decode routine shipped right
next to them — is usually the tell that something sensitive is hiding among
noise rather than being protected.

### A privileged credential hiding among them

The most damaging version is a credential pair (an ID and a token, an API
key, a session hint) that, once decoded, is directly usable against another
endpoint to authenticate as a higher-privileged account. At that point the
"obfuscation" has become the entire authentication boundary for a privilege
escalation.

## How to recognise it in an authorized lab

- View page source and search for inline `<script>` blocks, especially on
  pages reachable right after a normal login.
- Look for any function with a name like `_x`, `decode`, `unscramble`, or
  similar, and any array of objects that all look the same shape (a name
  plus an encoded string).
- Read the decode function itself — it is client-side code, so it is always
  fully visible — and run it yourself (DevTools console, or a short script)
  against every encoded value, not just the one that looks most interesting.
- Check what each decoded value is accepted by. A token that looks inert in
  isolation can be exactly what a secondary login or support endpoint
  expects.

## Common mistakes and false assumptions

### "It's Base64, not plaintext, so it's safe"

Base64 is an encoding, not a cipher. It has no key and no secret step; any
browser, and any attacker, decodes it for free.

### "XOR with a custom key counts as encryption"

A single-byte (or short, reused) XOR key recovered from the same JavaScript
file that uses it is not a secret — it is public the moment it ships.
Real encryption requires a key the attacker does not have.

### "Mixing in decoys makes it secure"

Decoys raise the number of values an attacker has to try, not the
difficulty of trying each one. If decoding is free, trying three or thirty
entries is still free.

## Impact

Depending on what the leaked value unlocks, this ranges from information
disclosure up to full account takeover or privilege escalation — in the
worst case, a leaked administrative credential turns a low-privilege account
into an admin one with a single follow-up request.

## How developers prevent it

- Never compute or embed a real secret or credential server-side into a
  response the client will see, authenticated or not.
- If the client genuinely needs a capability, issue it a short-lived,
  narrowly-scoped token server-side, instead of a shared or admin credential.
- Treat anything shipped to the browser as public. If it would be a problem
  for a user to read it, it should never reach their browser in the first
  place.
- Use real, audited cryptography only when confidentiality is actually
  required, and remember even that does not protect a key that is shipped
  alongside the ciphertext.

## FAQ

### Isn't this just "security through obscurity"?

Yes — and the lesson is the same one that term always teaches: obscurity is
not a substitute for an actual access control, because anything available
to a legitimate client is available to an attacker who can also be that
client.

### How is this different from a hardcoded secret in source code?

A secret hardcoded in server-side source is bad because anyone with code
access can read it. A secret shipped to the client is worse — anyone who
can simply view the page can read it, no code access required.

### What should I keep in a lab writeup?

Capture where you found the script, the exact decode logic you reverse
engineered (or reused), the decoded value, and what that value let you do
next — the leak is only as interesting as what it unlocks.

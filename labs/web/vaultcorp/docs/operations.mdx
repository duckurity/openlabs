# Operations — VaultCorp

## Service topology

A single container (`vaultcorp`) runs the entire application — Razor Pages
UI, the Hangfire dashboard/worker, and static file serving — all on port
5000. SQLite persists to the named volume `vaultcorp_data`, mounted at
`/app/data`. There is no second service, no reverse proxy, and no external
dependency at runtime.

```
docker-compose.yml   -> build context: ./app, service: vaultcorp
app/Dockerfile           -> multi-stage build (sdk -> aspnet runtime)
app/                      -> application source
```

## Start the lab

```bash
cd "Web CTF Full"
docker compose up --build -d
```

The flag is defined as a fixed `ARG` default in `app/Dockerfile`. No `.env`
file or runtime flag configuration is required. Every build produces the
same flag, which matches the `flag_hash` recorded in `lab.yml`. The plaintext
flag is intentionally present in the Dockerfile and is written to
`/app/flag.txt` during image construction.

The app is then reachable at `http://localhost:5000`. First start also
runs `Database.EnsureCreated()`, so no separate migration step is needed.

## Image-layer handling of the flag

`FLAG` is defined by a fixed Docker build `ARG` default in `app/Dockerfile`
and written into `/app/flag.txt` in a `RUN` instruction. The plaintext flag
is therefore embedded in the Dockerfile and in the resulting **image's**
build layer, not only in the running container's filesystem. Every build
produces the same flag, matching the `flag_hash` in `lab.yml`. This has a
concrete consequence beyond just "the container has the flag at
`/app/flag.txt`, read-only": anyone who obtains the Dockerfile or the built
image itself (e.g. via `docker save`, `docker history`, registry access, or
inspecting a pushed image's layers) can recover the plaintext flag directly,
without running the container and without going through any of the six
intended stages. Docker build args are not a secrets mechanism and are not
expected to be — this is standard, well-documented Docker behavior, not a
bug specific to this lab.

This is an accepted, deliberate trade-off for this submission because the
flag is fixed and intentionally embedded in `app/Dockerfile` to match
`lab.yml`'s `flag_hash`. The lab is designed for local deployment through
`docker-compose.yml`, which builds the image from `app/`. The flag is not
generated afresh at build time, and deployers do not need to provide a
separate `.env` file or substitute a real `FLAG` value. Distributing the
Dockerfile or pre-built image makes the flag recoverable and must be
understood as part of this lab's design.

If this lab is ever deployed in a way where the image or its source is
shared with players who should not know the flag beforehand, this
flag-delivery mechanism would need to change (e.g. injecting the flag at
container **runtime**, via an environment variable or mounted file not
baked into any image layer, rather than at build time).

## Reset and temporary storage

The lab has no explicit "reset" endpoint — state lives entirely in the
SQLite volume and in-memory Hangfire storage. A full reset is:

```bash
docker compose down
docker volume rm bin_vaultcorp_data   # or the actual volume name docker compose created
docker compose up --build -d
```

A background job (`db-cleanup`, see Maintainer API reference below)
already removes tenants older than 6 hours automatically, so a long-running
instance self-prunes abandoned playthroughs without manual intervention.

## Maintainer API reference

This section documents the internal surface that exists purely as the
intended vulnerability chain's target — it is not meant to be used by
maintainers directly, but is recorded here since it is part of the running
application and its behavior should be understood before touching
anything else in `Program.cs`.

- `GET /internal/api/create?type=&method=&arg0=&arg1=` — creates a Hangfire
  job via reflection. Gated by `LocalRequestsOnlyAuthorizationFilter`
  (loopback-only). This is the intentional RCE primitive (VC-CTF-05 in
  `security-report.mdx`) — do not relax its loopback gate or expose it
  further; the whole point of the challenge is that it is reachable only
  via the SSRF chain.
- `GET /hangfire`, `/hangfire/recurring` — Hangfire's own dashboard,
  same loopback gate. Two recurring jobs are pre-registered:
  `db-cleanup` (runs nightly, prunes old tenants) and `maintenance-runner`
  (registered with `Cron.Never`, visible in the dashboard purely so the
  `CommandExecutorJob` type is discoverable there — this is the
  intentional in-fiction breadcrumb for the chain's final stage).

## Validation workflow

```bash
# 1. Build and start
cd labs/web/vaultcorp && docker compose up --build -d

# 2. Run the automated end-to-end solve
cd verify
pip install requests
python3 verify_solve.py --base-url http://localhost:5000
```

A successful run prints each of the 6 stages and the recovered flag, and
exits `0`. See `validation-report.mdx` for the current evidence this
produces.

### Focused regression

Re-run `verify_solve.py` after any change to `Program.cs`,
`UrlFetchService.cs`, `CommandExecutorJob.cs`, or the Hangfire
registration/authorization setup — these are the files every stage of the
intended chain depends on.

## Runtime controls

- **Network egress:** the container's Docker network (`internal_only`)
  was briefly set to `internal: true` for egress isolation, then
  reverted after the author's local `docker compose up --build` run on
  Docker Desktop (Windows) showed the published port (5000) was
  unreachable from the host — Docker Desktop's WSL2/Hyper-V networking
  layer does not reliably set up inbound port forwarding for an
  `internal: true` network, unlike native Linux Docker. The intended
  solve path never needs outbound egress (the SSRF target is always the
  container itself), so this is a straightforward trade — real-world
  Docker Desktop compatibility over additional defense-in-depth that the
  solve doesn't rely on. See `security-report.mdx`'s residual risk
  register for the implication.
- **Filesystem:** `wwwroot` is writable (`chmod -R 777`) so
  `CommandExecutorJob` can write output there; `/app/flag.txt` is
  read-only (`chmod 444`) after being written at build time.

## Application safeguards

- Per-tenant data isolation via `TenantId` filtering on every query that
  touches `Users`.
- Antiforgery tokens are enforced on all player-facing POST forms
  (Register, Login, SupportLogin, Admin/Import, Profile) by ASP.NET Core
  Razor Pages' default `AutoValidateAntiforgeryTokenAttribute` — the
  dashboard's own `IgnoreAntiforgeryToken = true` applies only to
  Hangfire's dashboard routes, not to the application's own forms.
- Outbound network egress is currently unrestricted at the Docker level
  (see "Runtime controls" above for why) — this is a known, accepted gap,
  not an oversight; see the residual risk register below.

## Residual risk register

| Risk | Status | Notes |
| --- | --- | --- |
| RCE primitive usable beyond the container | **Open** | `internal: true` was reverted — Docker Desktop (Windows/Mac) doesn't reliably publish ports on an internal network. The intended solve path never needs egress, but a player's own command execution is no longer network-isolated at the Docker layer. Acceptable for a single-player, locally-run lab; would need a different containment approach (e.g. an egress firewall rule, or a Linux-only deployment target) before any shared/hosted deployment. |
| Base image supply-chain drift | Mitigated | Both Dockerfile stages pinned to digests, not floating tags |
| Flag predictability | **Known / intentional** | The flag is fixed in `app/Dockerfile` and matches `lab.yml`'s `flag_hash`. It is not randomly regenerated on each build and can be recovered from the Dockerfile or image layers. |
| Automated dependency/image vulnerability scan | Not yet run | No CI scanning pipeline has been run against this lab from this environment; recommend running the catalog's standard scan before merge |
| Long-running instance resource growth | Mitigated | `db-cleanup` recurring job prunes tenants older than 6 hours |

## Troubleshooting

- **Build fails pulling base images:** confirm the pinned digests in
  `app/Dockerfile` are still valid manifests (`docker buildx imagetools
  inspect <image>@sha256:...`); Microsoft occasionally deprecates very old
  tags, though pinned digests themselves do not expire.
- **`verify_solve.py` times out at Stage 6:** the Hangfire worker may not
  have picked up the job yet — increase `--poll-attempts` /
  `--poll-interval`, or confirm the worker count (`WorkerCount = 4` in
  `Program.cs`) hasn't been reduced to 0 in a local change.
- **SSRF bypass stops working after a change:** confirm
  `UrlFetchService.BlockedPatterns` still excludes `127.1` (or whichever
  alternate literal the solve path relies on) — any change to that list
  should be re-validated against `verify_solve.py` before merging.

## Maintenance and change control

Any change to `UrlFetchService.cs`, `Program.cs`'s Hangfire/authorization
setup, or `CommandExecutorJob.cs` is change-controlled for this lab: it can
alter or break the intended chain. Re-run the full validation workflow
above after any such change, and update `security-report.mdx` and
`challenge-design.mdx` if the change alters the attack path itself.

## Repository hygiene

- The fixed flag plaintext is defined in `app/Dockerfile` as the `FLAG`
  build-argument default and is intentionally embedded in the image at build
  time. Its value matches `lab.yml`'s `flag_hash`; it is not sourced from
  `.env` or `docker-compose.yml`.
- `verify/__pycache__/` and other Python build artifacts are excluded via
  `verify/.gitignore`.
- All narrative and maintainer documentation lives under `docs/` — the
  original separate `documentation/` folder was folded in and removed
  (see `docs/README.md` for what moved where).

# Validation report — dual-check

## Current deployment review

This report records what has actually been verified for `dual-check` as
of this submission, and what still needs independent re-checking by a
reviewer — written honestly about the limits of what could be verified
from the authoring environment, rather than claiming coverage that
wasn't actually exercised.

## What the fix proves (closed)

The Linux-compiled test build was already strong evidence that the *fix
is correct and non-destructive*, and the byte-level ciphertext match
confirmed the shipped `checker.exe` embeds the current source. That gap
is now fully closed: the maintainer ran the exact documented solve
values (`r3v3rs3_m3_pl2` → quiz → `7` → `ch3ck3r_unl0ck_key` →
`2bb50ef99ea5dcea300e6efd3d8085e4`) live against the actual shipped
`game.exe` and `checker.exe` on a real Windows machine and recovered the
current flag, `duck{...}`, exactly. No
further re-solve is needed.

## Validation coverage

Covered by evidence above: flag format and hash correctness, the
surgical scope of the fix, full chain logic re-verification (on a
Linux-compiled equivalent), negative-path rejection, and `check.py`
correctness.

Now also covered: a fresh end-to-end *live, interactive* solve of the
exact shipped `game.exe` + `checker.exe`, run directly by the maintainer
on a real Windows machine (see the evidence ledger above) — recovered
the current flag exactly; and a real Microsoft Defender scan of both
shipped binaries on that same machine, finding no threats.

Still not covered: the platform decision (Windows-only vs. also
providing a Linux ELF build for headless CI) remains undecided — see
`README.md`'s "Delivery model" section, which currently documents
Windows-only as the design decision but notes no CI step exists to
validate that automatically yet. This is a scope/design decision for the
maintainer, not a verification gap.

## Documentation verification

`challenge-design.mdx` and `official-solution.mdx` were cross-checked
against the original narrative walkthrough and objective write-ups (now
folded into `official-solution.mdx` and `challenge-design.mdx`
themselves — see `docs/README.md` for what moved where) and the actual

`lab.yml`'s `techniques:` field intentionally stays commented out until
technique pages are authored and placed at `content/technique/<slug>.mdx`

them before they exist there would fail the catalog's own existence
check.

## Release decision

**Validation complete; not yet released.** `checker.exe` has been
rebuilt on Windows from the patched `checker.c`, confirmed byte-for-byte
to embed the current flag ciphertext, and — as of this pass — solved
live end-to-end on real Windows hardware, recovering the exact current
flag. Both shipped binaries have also been scanned with Microsoft
Defender with no threats found. No outstanding verification gaps remain
for this lab. Per the standing agreement for this submission, nothing is
pushed to `duckurity/openlabs` until all three proposed challenges
(VaultCorp, NexaWallet, and `dual-check`) are reviewed and agreed with
the maintainer on their respective sub-issues.

## Independent acceptance procedure (already completed once)

A reviewer can reproduce this lab's full acceptance independently, the
same way the maintainer already did for this report:

1. Run the shipped `bin/game.exe` directly (no rebuild needed — this was
   already verified against the current shipped binary): password
   `r3v3rs3_m3_pl2` → quiz → mini-game → confirm Password 2
   (`ch3ck3r_unl0ck_key`) is revealed.
2. Run the shipped `bin/checker.exe` with that password and hex value
   `2bb50ef99ea5dcea300e6efd3d8085e4`; confirm it prints
   `duck{...}`.
3. `python3 check.py "<printed flag>"` from the lab root; a `0` exit
   code and "Correct!" message is sufficient acceptance evidence.
4. Optionally, scan both binaries with any AV engine
   (`MpCmdRun.exe -Scan -ScanType 3 -File <path>` on Windows is a quick
   way) — already run once by the maintainer, with no threats found.

## Evidence handling

Every "Pass" above is either directly reproducible (the Python/CyberChef
reproductions, `check.py`, the Linux test build), was produced by the
challenge author on their own analysis (the original Ghidra walkthrough,
the `strings` scan), or was run live by the maintainer (`0xyouzv`) on
their own Windows machine against the exact shipped binaries (the
end-to-end solve and the Defender scan). No rows remain marked "Not
run" — the two gaps this report used to carry (the live interactive
solve, and the AV scan) were both genuinely blocked only by this
reviewer sandbox's lack of a Windows/Wine runtime and its network
allowlist, not by anything wrong with the lab, and have now been closed
by someone with the right environment.

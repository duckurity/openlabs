## Overview

A common, intuitively appealing design pattern is to stack several
independent-seeming client-side checks in front of a sensitive action —
tamper/instrumentation detection, a hidden or hard-to-reach UI step, a
liveness or sanity check on some internal state — reasoning that defeating
all of them together is harder than defeating any one alone. That
reasoning is correct about *effort*, and wrong about *security*: every
one of those checks, and the data they produce, exists and executes
entirely inside an environment the attacker fully controls. No amount of
layering changes that category of problem.

## Examples

### Detection as a gate instead of a signal

A check for root, Frida, Xposed, or a debugger is real, useful
*information* — but only if something outside the attacker's control
(a backend) gets to act on it. Used as a client-side gate (the kind of
"if tampered, block" pattern this is), it's exactly as trustworthy as
every other decision the attacker-controlled process makes about itself:
not at all, once the attacker can intercept the decision itself.

### A hidden screen as a second factor

Requiring the player to discover and reach a non-obvious UI path before
proceeding adds real *search effort* — but once found and reached (by
whatever means, including directly from code), it provides no additional
verification of *who* reached it or *why*. "Hard to find" is not the same
property as "requires legitimate authorization."

### A liveness check on internal state

Requiring that some granting function receive a genuinely live, real
object (not a trivially fabricated `null` or a fake value) raises the bar
above a one-line bypass — but it still only verifies "is this a real
instance of the expected type," not "did the real-world event this state
is supposed to represent actually happen." An attacker who can run
arbitrary code in the process can always obtain a genuinely live instance
of anything the process itself can construct.

### The proof of success

Even after legitimately satisfying every layered check, if the resulting
"proof that this was authorized" (a token, a flag, a receipt) is itself
computed by the same client, it inherits the same fundamental
untrustworthiness — it can be reproduced by anyone who reverse-engineers
the computation, with or without satisfying any of the checks that were
supposed to gate it.

## How to recognise it in a lab or a real app

- Multiple independent-seeming security checks all execute and are all
  evaluated within the same client binary/process, with no step handed
  off to a server for independent verification.
- The "proof" of a successful, privileged action is generated by
  client-side logic rather than issued by a backend after its own
  verification.
- Each individual check, examined alone, looks like reasonable security
  engineering (the checks in this lab are, individually, correctly
  implemented) — the weakness is structural, not a bug in any one check.

## Common mistakes and false assumptions

### "Multiple layers must add up to real security eventually"

Layering genuinely raises the cost and time an attacker needs — each
additional check is one more thing to diagnose and defeat — but it does
not change the category of the problem. A chain of entirely
client-side-enforced decisions is still, as a whole, a client-side-enforced
decision; the attacker ultimately needs to defeat a controlled, bounded
amount of additional effort, not something categorically different.

### "If I can't find a simple one-liner bypass, it must be secure"

The absence of a trivial bypass (a single hook, a single reflection call)
demonstrates the design raised the floor on required effort — a real,
worthwhile outcome — but says nothing about whether a determined attacker
with full process access can eventually succeed. For threat models that
need to resist exactly that attacker (anti-fraud, anti-cheat, mobile
banking), "eventually" is not an acceptable outcome, however distant.

### "This only matters for 'hacking' scenarios, not normal users"

The whole point of a security boundary is to hold against an adversarial
user — a normal, honest user never needed the check to begin with. A
design that only works against non-adversarial use was never providing
security in the first place.

## Impact

Any system that relies entirely on client-side logic for an
authorization decision it actually needs to trust — regardless of how
many independent-seeming checks are layered together — provides, at
most, a time/effort deterrent against a sufficiently motivated attacker
with full control of their own device. It does not provide an actual
trust boundary.

## How developers prevent relying on this as real security

- Identify which decisions in the system genuinely need to be
  trustworthy (not just "hard to tamper with") and move those, and only
  those, to a backend the attacker does not control — this does not mean
  every client-side check is useless, only that none of them, alone or
  combined, can substitute for this.
- Treat every client-side signal (tamper detection, device state, UI
  flow completion) as an *input* to a server-side decision, never as the
  decision itself.
- Any proof of a privileged action's success must be issued and signed
  by the backend after its own independent verification — never computed
  or minted by the client, however the computation is protected.

## FAQ

### Isn't SSL pinning a counter-example — a client-side check that does help?

Pinning protects the *confidentiality and integrity of a connection* to a
server that is itself making a real decision — it's valuable precisely
because there's a trustworthy party on the other end. It doesn't help, by
itself, make a purely client-side decision trustworthy, which is the
specific problem this technique is about.

### Does this mean client-side checks are pointless?

No — they raise attacker cost, catch unsophisticated attempts, and
provide useful telemetry when reported to a backend. "Not sufficient
alone" and "not worth having" are different claims; this technique is
specifically about the first one.

### What should I keep in a lab writeup?

For each individual check defeated, note that it was individually sound
(not a bug), and that the overall lesson is the cumulative/structural
one, not "this app had four separate mistakes" — that framing is useful
for both the technical writeup and for explaining the fix to a
non-technical stakeholder.

## Overview

A password reset code must authorize recovery of the account that requested it. Target confusion happens when a flow verifies a code but then accepts a different account identifier for the password update. The code and target are not bound to the same identity.

This is an account-recovery authorization failure. It can let someone who controls one account's mailbox change another account's password. The reset code can be strong, short-lived, and single-use while the flow remains vulnerable if its verified owner is ignored.

## Examples

A safe test uses two synthetic accounts in an authorized lab. Request a recovery code for the first account. Inspect whether confirmation derives the account from the verified recovery record or trusts a second client-supplied email or user ID. Verify that the response cannot change credentials for the other account.

A vulnerable implementation may validate a code against the authenticated requester, then update the account selected by a separate request field. The essential defect is the missing identity binding, not a weak code format.

Test the whole lifecycle. Check expiry, single use, concurrent confirmation, session invalidation, and errors for unknown accounts. Do not test this against accounts or systems you do not own or have permission to assess.

## Prevention

Bind the reset transaction to one immutable account identifier when the code is issued. After successful verification, derive the password-update target from that server-side record. Do not accept a second client-controlled target identity.

Store only a hash of a high-entropy code. Give it a short expiry and consume it atomically once. Send it through a verified recovery channel, avoid account-enumerating responses, and revoke existing sessions after a password change. Log recovery events without recording passwords, codes, or session tokens.

## FAQ

### Does a random reset code prevent this flaw?

No. A random code helps prevent guessing. The server still needs to bind that code to the one account it may recover.

### Is a reset code a session token?

It is a short-lived credential for one recovery action. Scope it to that action and account. Do not treat it as permission to select arbitrary users.

### How should a test demonstrate the boundary?

Use two disposable accounts. Confirm that the code issued for one account cannot change the other account's password, then verify that the intended account can still recover access.

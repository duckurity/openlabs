# CBC padding oracle

## Overview

A padding oracle occurs when an application decrypts attacker-controlled ciphertext and exposes whether the decrypted plaintext has valid padding. An attacker can alter a ciphertext block or IV and observe that response to recover protected plaintext without learning the encryption key.[1]

For CBC decryption, each plaintext block depends on the decrypted current ciphertext block XORed with the preceding ciphertext block; for the first block, the IV takes that preceding-block role. Carefully chosen changes can make candidate plaintext suffixes satisfy PKCS#7 padding. A stable difference between invalid padding and a later rejection supplies the oracle signal.

A padding oracle does not require a timing leak. Different status codes, response bodies, redirects, or other observable outcomes can be sufficient. OWASP describes a secure implementation as checking integrity and exposing only a generic success or failure, without side channels that reveal internal error states.[1]

## Examples

A safe test uses an authorized lab and its own ciphertext. Submit the original value, then change one byte of the IV or of the block before a target block and compare the outcomes. A vulnerable service separates inputs whose padding fails from inputs that pass padding but fail a later check. The separation can appear as a different status code, error field, message, or redirect, even when the service never returns plaintext.

A vulnerable implementation decrypts and unpads ciphertext before it verifies an independent MAC. The essential defect is the verification order, not the block cipher.

The defensive order is the opposite: authenticate the complete canonical envelope before decrypting or unpadding. Prefer a well-reviewed authenticated-encryption API that returns plaintext only on successful authentication and a single failure otherwise.[3][4] Keep error messages minimal and audience-appropriate.[2]

## FAQ

### Does the attack recover the encryption key?

No. The oracle can reveal plaintext from ciphertexts under the vulnerable service, but it does not reveal the key or forge the HMAC.

### Must every plaintext block be recovered?

No. Recover only the bytes needed to obtain the protected value. Additional plaintext recovery is not a challenge requirement.

### How should applications prevent the issue?

Authenticate before decrypting legacy CBC ciphertext, or use an authenticated-encryption mode through a maintained library. Return one generic failure for unauthenticated data; uniform text alone is not a substitute for correct verification order.[1][3][4]

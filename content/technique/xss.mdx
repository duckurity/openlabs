## Overview

Cross-site scripting happens when an application puts untrusted input into a page without preserving the boundary between text and markup. The browser receives input that looks like HTML or JavaScript, parses it as executable content, and runs it with the origin's privileges.

The important detail is the sink. A value that is echoed as text stays text. A value inserted through an API such as `innerHTML`, a server-rendered template without escaping, or a JavaScript string that is later evaluated can become markup or code. The same string can be harmless at one sink and dangerous at another.

> **Encoding is context-specific**
>
> HTML text, attribute values, URLs, JavaScript strings, and CSS each have different rules. One escaping routine does not protect every context.

## Examples

### Stored note rendered as HTML

A note service stores submitted text and an administrator later reviews it. The review page builds each note with:

```javascript
article.innerHTML = note.content;
```

If `note.content` contains an element with an event handler, the administrator's browser parses and executes it when the page loads. Because the page belongs to the application's origin, the payload can read a session cookie that is not marked `HttpOnly`.

A safer review page treats the note as text:

```javascript
article.textContent = note.content;
```

If limited formatting is required, a maintained allowlist sanitizer can run before insertion. A hand-written blocklist is not a substitute, because browsers accept whitespace, attribute variants, and parser edge cases that substring checks miss.

### The difference a sink makes

The same string can appear safely in a JSON response and dangerously in a page:

```text
stored value:  <svg\tonload =run()>
text sink:     shown literally
HTML sink:     parsed as markup
```

This is why a payload that is rejected in one field may work in another, and why validation must match the parser that ultimately consumes the value.

## FAQ

### Is XSS only a client-side problem?

The execution happens in a browser, but the cause can be server-side rendering, client-side DOM code, or a stored value that reaches either. Treat it as an application-wide output-handling problem.

### Does Content Security Policy replace output encoding?

No. CSP is defense in depth. It can reduce the impact of some payloads, but it does not make an unsafe sink safe, and a permissive policy may not block the payload at all.

### Why do filters sometimes miss an obvious payload?

Many filters search for exact substrings. HTML allows equivalent syntax through whitespace, quoting, casing, and parser differences. Use a real parser and a strict allowlist rather than trying to enumerate every dangerous string.

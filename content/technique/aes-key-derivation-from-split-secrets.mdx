## Overview

AES is real, well-reviewed cryptography — but encrypting data with it
only protects that data if the key stays secret from whoever has the
ciphertext. When a program derives its own AES key, at runtime, from
values the same program also obtains from (or computes using) the
client it's running on, the key is not actually secret from an attacker
who controls that client. This technique covers recognising that pattern
and reproducing the key derivation to decrypt the protected data
yourself.

## Why "the data is AES-encrypted" doesn't end the analysis

Finding AES in a binary (recognisable S-boxes, round constants, or a
named library) can look like a dead end — "it's encrypted, so it's
secure." The actual question is always: where does the key come from,
and who can obtain it? If the key is:

- hardcoded directly in the binary → trivially extractable, no
  different from any other embedded constant;
- derived from values the binary itself already reveals or computes
  (a password you recover, a value you compute via another technique) →
  equally extractable, just with one extra derivation step;
- derived from something genuinely outside the attacker's reach (a
  server-side secret, a hardware-backed key store) → actually protected.

Only the last case is real protection. The first two just add a
derivation step before the same underlying problem (a client-readable
key) applies.

## Examples

### Key folding from a password

A common pattern: fold an arbitrary-length password string into a
fixed-size key (for example, 16 bytes for AES-128) by XOR-ing and
rotating each character into a position based on its index. This is
reversible and fully reproducible once the password itself is known —
folding adds no secrecy, only a fixed transform.

### Combining two recovered values

A program might derive its final key as one recovered/computed value
XOR'd (or otherwise combined) with a second recovered/computed value —
intended to simulate "needing two pieces of information." Cryptographically,
XOR-combining two known values is as fully determined as either value
alone; once both inputs are known, the combination is a one-line
computation, not an additional barrier.

### Fixed IV and ciphertext shipped alongside the key material

For CBC-mode decryption you also need the initialization vector (IV) and
the ciphertext itself — both of which, in a purely client-side design,
ship in the same binary as everything needed to derive the key. Once you
have key, IV, and ciphertext, decryption is a single standard-library
call in any language, or a point-and-click operation in a tool like
CyberChef's "AES Decrypt."

## How to recognise it in a lab

- The binary contains recognisable AES constants/routines (or a note
  that it does) alongside a key-derivation function that takes one or
  more values you can either read directly or compute via a separate
  technique.
- The IV and ciphertext are both present as static data in the binary —
  not fetched from a network or derived from anything you can't see.
- The "protected" result (a flag, a license payload) is meant to be
  readable by the legitimate end user after a successful check, meaning
  the program itself must be able to fully derive the key and decrypt at
  runtime, on the user's own machine.

## Common mistakes and false assumptions

### "It's AES, so it's unbreakable"

AES itself (the cipher) is not what's being attacked here — the key
derivation is. No amount of cipher strength protects data once the
attacker can independently derive, or already has, the exact key used
to encrypt it.

### "Needing two separate values to derive the key adds real security"

It adds *effort* (you need to recover both values, possibly via
different techniques), but once both are known, combining them is
exactly as deterministic as using either value alone — there's no
additional cryptographic hardness from the combination step itself.

### "I need to break the key derivation function, not the cipher"

This framing is usually right in practice — but worth stating
explicitly, since it's easy to waste time trying to "attack" AES itself
in this kind of challenge, when the actual target is almost always the
(much weaker) logic that produces the key AES is given.

## Impact

Any encrypted payload protected only by a client-derivable key offers no
real confidentiality against an attacker willing to do the derivation —
the cipher's strength is irrelevant once the key itself is recoverable.

## How developers prevent relying on this

- Never derive an encryption key, at runtime, entirely from values that
  are themselves present in or computable from the same client-side
  artifact — if the program can derive the key, so can anyone running
  the program offline.
- If data genuinely needs to stay confidential from the end user running
  the program, the key (or the decryption itself) needs to live
  somewhere the user's own copy of the program cannot reach — typically
  a server-side service, or hardware-backed key storage the application
  can use but not directly read.
- Treat "we encrypted it" as a statement about implementation, not a
  substitute for actually answering "who holds the key, and can the
  person we're protecting this from ever obtain it?"

## FAQ

### Does this mean AES itself is somehow "weak" here?

No — AES-128-CBC is used correctly and is not the weak point. The
weakness is entirely in how the key is obtained: from values a
client-side attacker can fully recover, rather than from something kept
genuinely out of their reach.

### How would I know if a real system has this problem?

The same question that applies throughout this challenge: can the
program, running fully on a device you control, derive and use the key
itself? If yes, you can derive it too, no matter how the key is
constructed from there.

### What should I keep in a lab writeup?

Each input value's origin (which technique you used to recover or
compute it), the exact derivation step used to combine them into the
final key, and the IV/ciphertext you decrypted with it — this traces the
full chain from "nothing" to "plaintext flag" in a way a reviewer can
re-run.
